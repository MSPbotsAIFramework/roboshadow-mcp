## Requirement understanding

One line: Review endpoint security, asset inventory, vulnerability, and remediation-status data via RoboShadow.

The reporter wants MSPbots agents to be able to pull RoboShadow data for a managed tenant/organisation: which endpoints exist and their security posture (antivirus, firewall, Windows Defender), what hardware/software is installed on them, what vulnerabilities (CVEs) are outstanding, and the status of remediation/patching attempts. The ticket supplies no specific tool list, only a link to the generic conduit.wyre.ai plugin page (`https://conduit.wyre.ai/plugins/roboshadow`), which per [[reference_conduit_wyre_plugin_pages_are_generic]] (confirmed again on this page) adds nothing beyond the one-line description already in the ticket. There is no existing RoboShadow connector anywhere in MSPbotsAIFramework (confirmed 2026-10-30 in the earlier `[BLOCKED]` comment: org-wide search for "roboshadow" and variants across ~124 repos returned zero hits), so this is a new-connector build, not a change to an existing one.

- RoboShadow publishes an official, freely-reachable OpenAPI 1.1.0 spec (`https://cdn.development.roboshadow.com/publicapi/openapi.yaml`, fetched 200 OK 2026-10-30) covering 40 GET endpoints plus one POST auth endpoint, grouped under: Identity, Antivirus, Applications, Defender, Devices, Disks, Firewall, Hardware, MFA, Remediation, Services, Updates, Users, Vulnerabilities, Vulnerability Scanner (`scratch/PRD-21238/openapi.yaml`, `info.title`/`tags`). - Auth is `BearerAuth` (Firebase JWT) server-wide (`openapi.yaml` `components.securitySchemes.BearerAuth`, `security: [{BearerAuth: []}]`). The only way to obtain that JWT is `POST /identity/bearertoken`, which exchanges a long-lived Firebase **refresh token** for a short-lived (`expiresIn`, example `3600`s) access token (`openapi.yaml` `components.schemas.BearerTokenRequest`/`BearerTokenResponse`).
- Every other endpoint is read-only (`GET`) and scoped by `organisationId` (one credential can see more than one organisation — `GET /identity/organisation` lists them), so there is no "write" or "trigger a remediation" capability published by this API version; the ticket's wording ("review ... data") matches that: it does not ask for any action/trigger tool.

## Product design

### Goals / Non-goals

**Goals**
- Give an agent read access, scoped per tenant via a header-supplied RoboShadow credential, to:
  - the organisations the credential can see, and the users in one of those organisations;
  - the device/asset inventory of an organisation (devices, hardware, installed applications, disk shares, user profiles/local users);
  - endpoint-security posture (antivirus, ransomware protection, Windows Defender, firewall) at both the per-device and org-report level;
  - vulnerability data (CVE/CPE/application/device-level, plus per-CVE available fixes) at the org level and per device;
  - remediation-status data (the remediation report, and the specific CVEs addressed by one remediation attempt);
  - OS update/patch compliance (missing updates by device, org summary);
  - the Microsoft 365 MFA compliance report RoboShadow surfaces;
  - external vulnerability scan status/summary/scanned-IP overview.

**Non-goals**
- No device-management actions (reboot, isolate, push agent, trigger a scan or remediation) — the published API does not expose any such endpoint; there is nothing to design a write tool against.
- No real-time alerting/webhooks — not present in this API version.
- No support for the Firebase refresh-token *issuance* flow (how a tenant first obtains that refresh token from RoboShadow) — that happens entirely inside RoboShadow's own product, outside MSPbots. The connector only consumes an already-issued refresh token supplied via a request header (see Open questions, non-blocking).
- No OAuth flow — the vendor's only published auth mechanism is the static refresh token described above, so there is nothing to build beyond "read it from a header, exchange it per request."

### Acceptance criteria AC1..AC16

- **AC1**: Given a valid RoboShadow credential header, When `roboshadow_list_organisations` is called, Then it returns the organisations visible to that credential (id + name), with no required parameters.
- **AC2**: Given a valid credential and an `organisation_id`, When `roboshadow_list_organisation_users` is called, Then it returns that organisation's users; when `organisation_id` does not belong to the credential, Then it returns the `unauthorized` error envelope, not the raw vendor 403.
- **AC3**: Given a valid credential and `organisation_id`, When `roboshadow_list_devices` is called with no filters, Then it returns up to the default page size of devices (id, name, IP, online state, AV/application scores, critical/high CVE counts) with a `has_more` flag; When called with `search`/`sort_by`/`sort_desc`, Then the returned set reflects those filters.
- **AC4**: Given a valid `device_id`, When `roboshadow_get_device` is called, Then it returns that device's summary record; when `device_id` does not exist in the organisation, Then it returns the `not_found` envelope.
- **AC5**: Given a valid `device_id`, When `roboshadow_get_device_detail` is called with each of `section` ∈ {antivirus, applications, disks, services, updates, userprofiles, users, vulnerability_summary}, Then it returns that sub-resource for the device (paginated where the vendor endpoint itself paginates: applications, services, updates).
- **AC6**: Given a valid `device_id` and `disk_id` taken from that device's disk list, When `roboshadow_list_disk_shares` is called, Then it returns the shares exposed on that disk.
- **AC7**: Given a valid `organisation_id`, When `roboshadow_list_application_groups` is called with no `group_id`, Then it returns the organisation's installed-application groups; When called with a `group_id` from that list, Then it returns that group's detail (device count, affected devices).
- **AC8**: Given a valid `organisation_id`, When `roboshadow_get_report` is called with `report` ∈ {antivirus_summary, antivirus_by_device, antivirus_ransomware, antivirus_threats, antivirus_windows_defender, firewalls}, Then it returns the matching endpoint-security report for the organisation.
- **AC9**: Given a valid `organisation_id`, When `roboshadow_get_report` is called with `report` ∈ {vulnerabilities_summary, vulnerabilities_cves, vulnerabilities_cpes, vulnerabilities_applications, vulnerabilities_devices}, Then it returns the matching vulnerability report; When `roboshadow_get_cve_fixes` is called with a `cve_id` found in one of those reports, Then it returns the fixes available for that CVE.
- **AC10**: Given a valid `organisation_id`, When `roboshadow_get_report` is called with `report = "remediation"`, Then it returns the organisation's remediation attempts; When `roboshadow_get_remediation_cves` is called with an `attempt_id` from that report, Then it returns the CVEs addressed by that attempt.
- **AC11**: Given a valid `organisation_id`, When `roboshadow_get_report` is called with `report` ∈ {updates_by_device, updates_summary}, Then it returns the matching OS-update/patch-compliance report; filters (`critical`/`security`/`driver`/`rollup`/`other`/`workstations`/`servers`/`is_reboot_required`, `days`) narrow the `updates_by_device` result accordingly.
- **AC12**: Given a valid `organisation_id`, When `roboshadow_get_report` is called with `report` ∈ {hardware_by_device, hardware_summary, disks, disks_by_device, disks_summary}, Then it returns the matching hardware/disk report.
- **AC13**: Given a valid `organisation_id`, When `roboshadow_get_mfa_report` is called, Then it returns the Microsoft 365 MFA compliance report RoboShadow has for that organisation.
- **AC14**: Given a valid `organisation_id`, When `roboshadow_list_vulnerability_scans` is called, Then it returns the status of all external vulnerability scans for the organisation; When `roboshadow_get_vulnerability_scan_summary` / `roboshadow_get_scanned_ips` is called with a `scan_id` from that list, Then it returns that scan's summary / scanned-IP overview respectively.
- **AC15** (contract): Given a request to any RoboShadow tool with no `X-RoboShadow-Refresh-Token` header, When the tool is called, Then the server returns 401 listing the required header, not a 500 and not a silently-empty result.
- **AC16** (multi-tenant isolation, backend-anchored): Given two concurrent tool calls carrying two different tenants' `X-RoboShadow-Refresh-Token` values, When both resolve to RoboShadow access tokens and call the vendor API, Then neither request's derived access token or response data is visible to or reused by the other call (no cross-request/cross-tenant caching of the exchanged token).

## Tech design

### Conclusion

Build `roboshadow-mcp` from scratch (empty scaffold today) as a standard MSPbots vendor-MCP Python/FastMCP service: a thin per-tool mapping over RoboShadow's public OpenAPI surface, consolidated into 14 agent-facing tools (not a 1:1 mirror of the 40 vendor endpoints) to stay well under the 20-tool ceiling and keep tool choice legible to an agent. Credential is a single header carrying the tenant's RoboShadow refresh token; the service exchanges it for a RoboShadow access token once per incoming MCP request (never cached across requests) and calls the vendor API with it. No new infrastructure, no database, no change to any other repo.

### Where the current implementation lives

Nothing — `roboshadow-mcp`@a5fb393 is a 2-line README with no code (`README.md`:1-2). This is a greenfield build. The file layout and middleware pattern below are not invented from scratch; they follow the pattern already used by sibling MSPbotsAIFramework MCP repos built under the same `vendor-mcp-development` SOP, observed in this session via their ac.json test references (not this repo's own code, since none exists yet):
- `domotz-mcp` (`docs/tickets/PRD-21260.ac.json`, cached locally this session): tests under `tests/test_tools.py`.
- `datto-rmm-mcp` (`docs/tickets/PRD-21198.ac.json`, cached locally this session): tests split across `tests/test_alerts.py`, `tests/test_paging.py`, `tests/test_middleware.py`, `tests/test_isolation.py`.

### Option analysis

| Option | Approach | Pros | Cons | Verdict |
|---|---|---|---|---|
| A | 1 tool per vendor endpoint (~40 tools) | Simplest mental mapping from spec to code | Blows the SOP's 20-tool ceiling nearly 2x; most "report" tools differ only by URL suffix — an agent has to pick among 19 near-identical `roboshadow_get_*_report` tools instead of one tool with a `report` argument | Rejected |
| B | Consolidate by capability: one `report` tool with an enum covering the 19 org-level report endpoints, one `device_detail` tool with a `section` enum covering 8 per-device sub-resource endpoints, keep genuinely distinct resources (devices, disk shares, application groups, remediation-CVE drill-down, CVE-fix drill-down, vulnerability scanner, MFA, organisations/users) as their own tools | 14 tools total, well under the ceiling; each tool name still maps to one coherent capability; matches SOP A4 ("tools are capabilities, not endpoint mirrors") | A single `report`/`section` argument hides the exact endpoint name from the agent's tool list, so the correct values must be documented clearly in each tool's description/enum | **Chosen** |
| C | Group everything into 2-3 giant tools (e.g. one `roboshadow_query` tool with a `resource` + `action` free-form pair) | Fewest tools possible | Loses per-capability `readOnlyHint`/parameter typing granularity that MCP clients use for safety and UX; turns the tool into an untyped mini-DSL, which SOP A4 explicitly warns against (tools are not internal-API mirrors, but they also should not become a single opaque dispatcher) | Rejected |

For credential handling there is no real alternative: the vendor's only published auth mechanism is refresh-token → bearer JWT via `POST /identity/bearertoken` (no API keys, no OAuth). The only design choice is *when* to do the exchange — see Decision 3 below.

### Data & API contract

**Credential header** (declared in README, read by `middleware.py`):

| Header | Required | Meaning | Where to get it |
|---|---|---|---|
| `X-RoboShadow-Refresh-Token` | yes | Firebase refresh token for the tenant's RoboShadow account | RoboShadow account settings (exact menu path not yet confirmed — Open Questions) |

**Per-request auth flow** (not a tool — internal to every tool call):
```
POST https://api.roboshadow.com/identity/bearertoken
Body: {"refreshToken": "<value of X-RoboShadow-Refresh-Token>"}
-> {"accessToken": "<JWT>", "expiresIn": 3600}
```
The resulting `accessToken` is used as `Authorization: Bearer <accessToken>` for the rest of that single incoming MCP request only, then discarded (see Decision 3 and AC16).

**Tools** (all `readOnlyHint: true` — the vendor API publishes no write endpoint other than the internal token exchange above, which is not exposed as a tool):

| Tool | Vendor endpoint(s) | Key params |
|---|---|---|
| `roboshadow_list_organisations` | `GET /identity/organisation` | — |
| `roboshadow_list_organisation_users` | `GET /identity/organisation/{organisation_id}/users` | `organisation_id` |
| `roboshadow_list_devices` | `GET /windows/organisation/{organisationId}/device` | `organisation_id`, `page`, `page_size`, `search`, `sort_by`, `sort_desc` |
| `roboshadow_get_device` | `GET /windows/organisation/{organisationId}/device/{deviceId}` | `organisation_id`, `device_id` |
| `roboshadow_get_device_detail` | 8 endpoints under `.../device/{deviceId}/{antivirus,applications,disks,services,updates,userprofiles,users,report/vulnerabilities/summary}` | `organisation_id`, `device_id`, `section` (enum of the 8) |
| `roboshadow_list_disk_shares` | `GET .../device/{deviceId}/disks/{diskId}/shares` | `organisation_id`, `device_id`, `disk_id` |
| `roboshadow_list_application_groups` | `GET .../applications/groups` + `GET .../applications/groups/{group_id}` | `organisation_id`, `group_id` (optional — list vs. detail) |
| `roboshadow_get_report` | 19 endpoints under `.../reports/{antivirus,disks,firewalls,hardware,remediation-report,updates,vulnerabilities}/...` (every report endpoint except the two with an extra id segment, see below) | `organisation_id`, `report` (enum of 19), plus whichever of `page`/`page_size`/`days`/`search`/`sort_by`/`sort_desc`/update-filters apply to that `report` value |
| `roboshadow_get_remediation_cves` | `GET .../reports/remediation-report/{attemptId}/cves` | `organisation_id`, `attempt_id` |
| `roboshadow_get_cve_fixes` | `GET .../reports/vulnerabilities/cves/{cveId}/fixes` | `organisation_id`, `cve_id` |
| `roboshadow_list_vulnerability_scans` | `GET /vscanner/scans/{organisationId}/status` | `organisation_id`, `page`, `page_size`, `sort_by`, `sort_desc`, `is_scheduled`, `status` |
| `roboshadow_get_vulnerability_scan_summary` | `GET /vscanner/scans/{organisationId}/summary/{scanId}` | `organisation_id`, `scan_id` |
| `roboshadow_get_scanned_ips` | `GET /vscanner/scans/{organisationId}/ips-overview/{scanId}` | `organisation_id`, `scan_id` |
| `roboshadow_get_mfa_report` | `GET /microsoft/report/mfa` | `organisation_id`, `page` (vendor calls it `skipPages`) |

`report` enum values for `roboshadow_get_report`: `antivirus_summary`, `antivirus_by_device`, `antivirus_ransomware`, `antivirus_threats`, `antivirus_windows_defender`, `disks`, `disks_by_device`, `disks_summary`, `firewalls`, `hardware_by_device`, `hardware_summary`, `remediation`, `updates_by_device`, `updates_summary`, `vulnerabilities_summary`, `vulnerabilities_cves`, `vulnerabilities_cpes`, `vulnerabilities_applications`, `vulnerabilities_devices`.

**Response shape** (every list-shaped tool): the vendor returns `{"pagedData": [...], "totalItems": N}` (`openapi.yaml` `components.schemas.PagedResponse`); tools reshape this to `{"items": [...], "total": N, "has_more": bool[, "next_offset": N]}` and trim each item to the fields an agent plausibly needs (e.g. `roboshadow_list_devices` returns `{id, device_name, ip_address, is_online, agent_version, antivirus_score, cves_critical, cves_high}` rather than the full ~20-field vendor `Device` object) — per SOP A4 token-economy rule, not the vendor's raw payload.

**Error mapping** (vendor HTTP status → SOP error-envelope `code`):

| Vendor status | Envelope `code` | Notes |
|---|---|---|
| 400 (bad refresh token, bad request params) | `invalid_argument` (bad params) or `unauthorized` (bad token at exchange time) | distinguished by which call failed |
| 401 (at vendor, after exchange — token already expired mid-request) | `unauthorized` | |
| 403 (organisation/device not visible to this credential) | `unauthorized` | do not leak whether the id exists — same code as a genuinely bad credential |
| 404 (not documented in the spec, but device/scan/attempt/CVE path 404s are plausible) | `not_found` | |
| 429 | `rate_limited` | retry with backoff first (client.py), surface only if retries exhaust |
| 5xx | `upstream_error` | |
| missing `X-RoboShadow-Refresh-Token` header | HTTP 401 at the MCP layer (not a tool error envelope — this is the SOP §3.2 contract-level 401) | body lists the required header |

**Backward compatibility**: not applicable — new connector, no existing tenants/tool consumers.

### Key flow / sequence

```
Agent -> Gateway -> roboshadow-mcp /mcp (tools/call, header: X-RoboShadow-Refresh-Token)
  roboshadow-mcp middleware: header present? no -> 401 (required header list), stop
                              yes -> POST /identity/bearertoken {refreshToken} -> accessToken
                                     store accessToken in request-scoped ContextVar
  roboshadow-mcp tool fn: validate args -> client.py GET <vendor endpoint> (Authorization: Bearer accessToken)
                           vendor 2xx -> reshape {pagedData,totalItems} -> {items,total,has_more}
                           vendor 4xx/5xx -> map to error envelope (table above)
  middleware finally: reset ContextVar (accessToken discarded, never reused by the next request)
roboshadow-mcp -> Gateway -> Agent
```

### Non-functional

- **Idempotency & concurrency**: every tool is a GET-equivalent read; no write path exists, so there is no idempotency concern. Concurrency is handled by request-scoped `ContextVar` (SOP §3.3/§3.4) — two concurrent requests never share the exchanged access token.
- **Performance**: vendor responses are paginated server-side (`page`/`itemsPerPage`, vendor hard cap 100); this service additionally enforces its own default 50 / hard cap 200 and a 20,000-char response-size cap per SOP A4, truncating with `has_more` rather than ever returning an unbounded list.
- **Security**: credential read only from the `X-RoboShadow-Refresh-Token` header, never from env/config (SOP §3.1); never logged or persisted; the derived access token lives only in the request-scoped `ContextVar` for the duration of one request (AC16); 403s from the vendor are mapped to the same `unauthorized` code as a bad credential so the connector does not confirm/deny which organisation IDs exist to a credential that cannot see them.
- **Multi-tenant isolation**: `organisation_id` is an explicit required argument on every tool (no implicit "current org"); the access token used for a call is scoped to whatever `X-RoboShadow-Refresh-Token` that call's own request carried, never a token derived from a different request.
- **Observability**: structured log line per tool call (tool name, organisation_id, vendor status code, latency) with the refresh-token and access-token values redacted; `/health` is a pure local liveness probe per SOP §1.1, independent of RoboShadow's own uptime.

### Effort & breakdown

Rough order of magnitude: **2–3 person-days** for the dev leg (scaffold + middleware + client + 14 tools + unit/middleware/isolation tests + README + Dockerfile), given the API surface is fully specified by the OpenAPI doc and the project structure follows an established team pattern. Main uncertainty is the field-level shape of a few less-common reports (e.g. `antivirus_windows_defender`, `vulnerabilities_cpes`) where the spec's schema is present but not independently verified against live data (see manual test cases). Suggested sub-tasks (each independently verifiable): (1) scaffold + middleware + auth exchange + `/health`; (2) organisation/device/application-group/disk-share tools (AC1-7); (3) report + CVE-drill-down tools (AC8-13); (4) vulnerability-scanner + MFA tools (AC13-14); (5) README + Dockerfile + `gitleaks` + `tools/list` snapshot test.

### Risks & dependencies

- **Risk**: field-level response shapes for several report endpoints are taken from the OpenAPI schema only, not a live call (no test account) — if RoboShadow's actual responses diverge from the published schema, the field-trimming in `tools.py` could drop or mis-key a field. Mitigation: the manual test-case list above exists specifically to catch this once a trial account is available; it does not block shipping per SOP (`references/mcp-track.md` §2.5).
- **Risk**: the refresh-token → access-token exchange happens on every single tool call (never cached), adding one extra HTTP round-trip (typically <200ms) per tool call. Accepted as the cost of strict request-level isolation (SOP §3.3/§3.4) rather than building a shared token cache, which is exactly the pattern the platform's "no cross-request state" rule exists to prevent.
- **Dependency**: none on any other ClickUp ticket or repo — this is a self-contained new connector with no platform-side changes required (`Track: vendor-mcp`, no gateway change needed; all data access is per-request, header-scoped).

### Decisions made by DEV01

- **Consolidated 40 vendor endpoints into 14 tools** (Option B above) instead of a 1:1 mirror — why: SOP caps tools at 20 and asks for capability-shaped tools, not endpoint mirrors; alternative (40 tools) was rejected as it both breaks the cap and gives an agent 19 near-identical `get_*_report` tools to choose among instead of one tool with a `report` argument.
- **All 14 tools are `readOnlyHint: true`** — why: the published API has no write/action endpoint besides the internal token exchange, which is not itself exposed as a tool; there was no read/write split to design.
- **Single credential header `X-RoboShadow-Refresh-Token`, exchanged per-request, never cached beyond that request** — why: the vendor's only published auth mechanism is refresh-token→JWT; request-scoped exchange satisfies the platform's "no cross-request/cross-tenant state" rule without a shared token cache. Alternative (cache the access token for its `expiresIn`) was rejected because it requires shared state keyed by tenant, which is exactly what the platform rule forbids.
- **`organisation_id` (and `device_id`/`scan_id`/etc.) are explicit required parameters everywhere, never auto-resolved to "the only organisation"** — why: one credential can see more than one organisation (`GET /identity/organisation` returns a list); silently defaulting to "the first/only one" works today and breaks ambiguously the day an MSP has two. `roboshadow_list_organisations` exists precisely so an agent can discover the right id first.
- **Pagination default 50 / hard cap 200, overriding the vendor's own default 10 / max 100** — why: SOP's token-economy rule sets the floor/ceiling for this platform regardless of what an individual vendor defaults to; the vendor's own max (100) sits below our hard cap, so in practice the vendor's `itemsPerPage=100` is the real ceiling enforced downstream — documented here so the dev leg doesn't just forward the raw vendor envelope uncapped.

To change any of these, say so in a comment and move the ticket back to 5b - ready for groom.
